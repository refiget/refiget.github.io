理解 Git 的三棵树：工作区、暂存区与提交历史

Git 的日常操作看起来像是一组命令，其实背后是一套清晰的状态模型。理解工作区、暂存区和提交历史之间的关系，就能更从容地使用 add、commit、restore 和 reset。

先看三个状态区域

可以把 Git 的基本工作过程想成三个区域之间的内容流动：

  1. 工作区（Working tree）：磁盘上正在编辑的项目文件。
  2. 暂存区（Index）：下一次提交准备收录的内容快照。
  3. 提交历史（Repository）：已经保存下来的提交，以及它们之间的关系。

这里常说的“三棵树”是帮助理解状态的比喻。实际使用时，暂存区是一个索引文件，提交则保存项目在某个时刻的快照。

git add：选择要提交的内容

修改文件后，变化首先只在工作区。运行 git add 会把指定路径当前的内容放入暂存区。它不是简单地“标记一个文件”，而是更新下一次提交将采用的文件版本。

git add src/app.js
git status

这让暂存区成为一次提交的预览和边界。你可以先完成一个改动、加入暂存区，再继续编辑另一个改动；后续编辑不会自动进入已经暂存的快照。

git commit：保存暂存区快照

git commit 会基于暂存区创建新的提交。提交记录包含项目快照、提交说明，以及指向父提交的引用。它不会把工作区中所有未暂存的变化一并保存。

git commit -m "Add app configuration"

因此，提交前查看 git status 很有帮助：它会分别列出已暂存和未暂存的变化。

撤销时，先确认要改哪个区域

很多 Git 命令的差别，在于它们改变哪个区域：

  • git restore file：用暂存区的版本恢复工作区文件。
  • git restore --staged file：把文件从暂存区移出，工作区内容保留。
  • git reset --soft HEAD~1：移动当前分支引用，保留暂存区和工作区。
  • git reset --mixed HEAD~1：移动分支引用并重置暂存区，保留工作区内容。

这些命令作用不同。执行前先运行 git status，并确认目标是工作区、暂存区，还是提交历史。

一个实用的心智模型

把 Git 想成三个阶段：在工作区修改，在暂存区挑选快照，再把快照保存为提交。遇到命令行为不确定时，问自己两个问题：当前内容在哪个区域？这条命令会改变哪个区域？

当这两个问题有了答案，Git 就不再像一堆需要死记硬背的命令，而更像一套可以推理的文件状态管理工具。
